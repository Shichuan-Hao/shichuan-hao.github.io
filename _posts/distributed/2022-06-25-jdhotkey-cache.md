> 在大促时期（618/双11），少量商品会占据绝大多数的流量——这就是"热点"。JDhotkey 是京东开源的热点缓存探测系统，能在毫秒级发现热点 key 并自动构建本地缓存，将热点流量从 Redis 集群转移到应用本地。本文剖析其核心架构和工作原理。

## 一、热点缓存问题

### 1.1 什么是热点 Key？

**热点 Key** = 在某一时间段内被大量访问的缓存 Key。典型的场景：
- 大促商品详情页（iPhone 15 降价）
- 突发新闻详情
- 热门视频的评论列表

### 1.2 热点缓存带来的问题

```
正常流量 → Redis 集群 → 按 Slot 分散到多个节点 → OK

热点流量 → Redis 集群 → 全部打到同一个 Slot → 单节点 CPU 打满
                                              → 网络带宽占满
                                              → 影响同节点其他 Key
                                              → 雪崩！
```

> 热点 Key 的问题是：99% 的流量聚集在 1% 的 key 上，直接打破了 Redis Cluster 的分片均衡假设。

### 1.3 传统方案的局限

| 方案 | 问题 |
|------|------|
| 多级缓存（Nginx+Lua） | 热点不固定时无法预加载 |
| Redis 多副本 | 热点流量不分散，多副本浪费资源 |
| 限流熔断 | 降级会影响所有用户，体验差 |

## 二、JDhotkey 架构

JDhotkey 是在京东内部广泛应用的热点缓存方案，后来开源到 GitHub。

### 2.1 整体架构

```
┌───────────────────────────────────────────────────────┐
│                  JDhotkey Dashboard                    │
│                    （控制台）                            │
├───────────────────────────────────────────────────────┤
│                  Worker 集群                           │
│              （热度计算 + 热点推送）                      │
├───────────────────────────────────────────────────────┤
│                  etcd 集群                             │
│              （配置中心 + Worker 注册）                   │
├────────────┬────────────┬────────────┬────────────────┤
│  应用实例A  │  应用实例B  │  应用实例C  │    ...          │
│  (SDK)    │  (SDK)    │  (SDK)    │                 │
│  本地缓存   │  本地缓存   │  本地缓存   │                 │
└────────────┴────────────┴────────────┴────────────────┘
```

### 2.2 核心组件

| 组件 | 职责 |
|------|------|
| **JDhotkey-Client（SDK）** | 嵌入应用，上报 key 访问次数，接收热点通知 |
| **JDhotkey-Worker** | 集群部署，聚合计算各应用的 key 访问量，判定热点 |
| **JDhotkey-Dashboard** | 管理平台，配置热点的阈值、生效规则 |
| **etcd** | Worker 集群的配置中心和注册中心 |

### 2.3 热点探测流程

```
1. 应用 SDK 统计每个 Key 的访问次数
      ↓
2. 定时上报给 Worker 集群
      ↓
3. Worker 聚合所有上报数据，滑动窗口计算热度
      ↓
4. 热度 > 阈值 → 标记为"热点 Key"
      ↓
5. Worker 下发热点 Key 到所有应用实例
      ↓
6. 应用 SDK 收到通知 → 将 Key 的数据缓存到本地 Caffeine/Guava
      ↓
7. 后续该 Key 的请求直接从本地缓存返回，不走 Redis
```

### 2.4 热点 Key 生命周期

```
正常 → 探测(滑动窗口) → 热点 → 主动维持 → 冷却 → 正常
```

- **探测阶段**：滑动窗口统计，默认 10 秒内 N 次访问
- **热点阶段**：每 1 秒上报一次，Worker 确认仍是热点则继续维持
- **冷却阶段**：访问量下降，不再维持热点 → 删除本地缓存

## 三、设计亮点

| 设计 | 说明 |
|------|------|
| **去中心化探测** | SDK 本地统计 + Worker 聚合，避免集中式计数器瓶颈 |
| **滑动窗口** | 精确判定"当前时间段"的热点，而非全局统计 |
| **Push 模式** | Worker 主动推送热点 Key，SDK 本地预缓存 |
| **etcd 协调** | Worker 集群高可用，自动选举 Leader |
| **轻量级** | 不侵入业务代码，通过注解/配置即可接入 |

---

## 四、总结

| 维度 | 要点 |
|------|------|
| 问题 | 1% 的热点 key 占据 99% 流量 → Redis 单节点打满 |
| 方案核心 | SDK 本地统计 + Worker 聚合 + 滑动窗口 + 热点推送 |
| 关键组件 | Client SDK / Worker 集群 / Dashboard / etcd |
| 热点判定 | 滑动窗口 + 阈值 + 规则 |
| 本地缓存 | Caffeine/Guava，热点 Key 不再走 Redis |
| 适用场景 | 大促电商、热点新闻、爆款内容 |
