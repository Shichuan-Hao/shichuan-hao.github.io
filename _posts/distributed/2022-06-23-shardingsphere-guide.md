> 当单表数据量突破千万级别，MySQL 的查询、写入、备份都会急剧退化。ShardingSphere 作为 Apache 顶级项目，提供了一站式的分库分表、读写分离、数据加密和分布式主键解决方案。本文覆盖产品介绍、核心分片策略和 CosID 分布式 ID 生成器。

## 一、分库分表：为什么和是什么

### 1.1 单表单库的瓶颈

| 瓶颈 | 表现 |
|------|------|
| **连接数** | MySQL 最大连接数有限（默认151），连接池不能无限开 |
| **存储空间** | 单表数据磁盘占用过大，备份/恢复时间长 |
| **IO 瓶颈** | 磁盘 IOPS 是硬限制，读写到达上限后无解 |
| **DDL 变更** | 大表加字段可能锁表数小时 |

### 1.2 三种数据分片

| 分类 | 说明 | 示例 |
|------|------|------|
| **垂直分库** | 按**业务**拆分到不同库 | 用户库 / 订单库 / 商品库 |
| **垂直分表** | 按**字段**拆分到不同表 | 基本信息表 / 扩展信息表 |
| **水平分库** | 按**数据行**拆分到多个库 | 订单库_0 / 订单库_1 |
| **水平分表** | 同库内按**数据行**拆到多表 | order_0 / order_1 |

> 水平分库 + 水平分表是应对大数据量的**核心手段**。

## 二、ShardingSphere 产品生态

Apache ShardingSphere 定位为**数据库增强中间件**，由三大产品组成：

| 产品 | 定位 |
|------|------|
| **ShardingSphere-JDBC** | 轻量级 Java 框架，以 jar 包提供。**推荐首选** |
| **ShardingSphere-Proxy** | 独立数据库代理，支持异构语言 |
| **ShardingSphere-Sidecar**（规划中） | 云原生 sidecar 模式 |

### ShardingSphere-JDBC 架构

```
应用程序
    │
    ▼
ShardingSphere-JDBC（逻辑数据源）
    │
    ├─→ 数据库 ds0 ─→ 表 t_order_0, t_order_1
    └─→ 数据库 ds1 ─→ 表 t_order_0, t_order_1
```

**核心概念**：

| 概念 | 说明 |
|------|------|
| **逻辑表** | 应用操作的统一表名，如 `t_order` |
| **真实表** | 物理存在的分片表，如 `t_order_0` |
| **分片键** | 决定数据落在哪个库/表的字段 |
| **分片算法** | 哈希取模 / 范围分片 / 自定义 |

### 四种分片策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **Standard（标准）** | 单个分片键精确分片 | 按 user_id 哈希 |
| **Complex（复合）** | 多个分片键组合分片 | 按 user_id + order_id |
| **Hint（强制）** | 应用层指定数据源 | 特殊路由需求 |
| **Inline（行表达式）** | 简洁的 Groovy 表达式 | `ds$->{user_id % 2}` |

## 三、CosID 分布式主键生成

### 3.1 分库分表后的主键挑战

单库时代用 `AUTO_INCREMENT` 没问题。分库分表后，多个库的自增 ID 会**重复**！需要一个全局唯一的分布式 ID。

### 3.2 分布式 ID 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| **UUID** | 本地生成，无依赖 | 字符串过长，无序，索引不友好 |
| **雪花算法** | 趋势递增，性能好 | 依赖机器时钟，时钟回拨可能重复 |
| **数据库号段** | 连续递增，简单可靠 | 有单点瓶颈 |
| **Redis 自增** | 高性能 | 需要额外运维 |

### 3.3 CosID 的设计

CosID 是 ShardingSphere 生态的分布式 ID 生成器，整合了**号段模式**和**雪花算法**：

```
CosID
  ├── SegmentId（号段模式）
  │      从数据库批量获取 ID 号段
  │      如一次分配 1000 个 ID → 只用访问 1 次数据库
  │
  └── SnowflakeId（雪花算法）
          MachineId 通过 ZK/K8s 自动分配
          解决时钟回拨问题
```

**雪花算法 ID 结构**：

```
┌─────────────┬───────────────┬───────────────┬──────────────┐
│  41位时间戳   │  10位机器ID    │  12位序列号    │   1位保留     │
│  (69年)     │  (1024节点)   │  (4096/ms)    │              │
└─────────────┴───────────────┴───────────────┴──────────────┘
```

## 四、总结

| 维度 | 要点 |
|------|------|
| 分片类型 | 垂直分库/分表（业务维度）+ 水平分库/分表（数据维度） |
| 核心架构 | 逻辑表（统一入口）→ 分片算法 → 真实表 |
| 分片策略 | Standard / Complex / Hint / Inline |
| 分布式 ID | CosID = 号段模式 + 雪花算法，解决时钟回拨 |
| ShardingSphere | JDBC（轻量） / Proxy（独立代理） |
| 选型建议 | 轻量场景用 CosID，复杂场景可整合美团 Leaf |
