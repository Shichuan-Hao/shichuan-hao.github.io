> 本文深度剖析 G1（Garbage-First）收集器的 Region 架构与 Mixed GC 机制，以及新一代 ZGC 的颜色指针、读屏障等革命性技术，并给出大内存高并发场景的选型实践建议。

## 一、 G1 收集器

`-XX:+UseG1GC`

G1（Garbage-First）是一款面向服务器的垃圾收集器，主要针对配备**多颗处理器及大容量内存**的机器。以极高概率满足 GC 停顿时间要求的同时，还具备高吞吐量性能特征。

### 1.1 Region 内存布局

G1 将 Java 堆划分为多个大小相等的独立区域（**Region**），JVM 最多可以有 **2048 个 Region**。

> 一般 Region 大小 = 堆大小 / 2048。如堆 4096M，则 Region 大小为 2M。也可用 `-XX:G1HeapRegionSize` 手动指定，但推荐默认计算方式。

![G1 Region 布局]({{ '/assets/img/jvm/g1-zgc/page1_img1.png' | relative_url }})

**核心特点**：

- G1 保留了年轻代和老年代的概念，但不再是**物理隔阂**，而是（可以不连续）Region 的集合- 一个 Region 可能之前是年轻代，回收后又变成老年代——**区域功能动态变化**- 默认年轻代占堆 5%（通过 `-XX:G1NewSizePercent` 设置），运行时 JVM 会自动给年轻代增加 Region，最多不超过 60%（通过 `-XX:G1MaxNewSizePercent` 调整）
- Eden 和 Survivor 对应 Region 默认比例 **8:1:1**

### 1.2 Humongous 大对象区

G1 有专门分配大对象的 Region 叫 **Humongous 区**，而不是让大对象直接进入老年代。

| 规则 | 说明 |
|------|------|
| 判定标准 | 大对象超过一个 Region 大小的 **50%** |
| 存储方式 | 一个超大对象可能横跨多个 Region |
| 设计目的 | 短期巨型对象专用，节约老年代空间，避免因老年代不够而 GC |
| 回收时机 | Full GC 时一并回收 |

![Humongous 区示意]({{ '/assets/img/jvm/g1-zgc/page1_img2.png' | relative_url }})

### 1.3 G1 运作过程

```mermaid
sequenceDiagramparticipant GC as GC 线程 participant App as 用户线程
    
    Note over GC,App: 🔴 初始标记（STW）
    App-->>App: 暂停 GC->>GC: 记录 GC Roots 直接引用对象
    
    Note over GC,App: 🟢 并发标记 App->>App: 正常运行 GC->>GC: 遍历整个对象图
    
    Note over GC,App: 🔴 最终标记（STW）
    App-->>App: 暂停 GC->>GC: 修正并发标记期间变动
    
    Note over GC,App: 🔴 筛选回收（STW）
    App-->>App: 暂停 GC->>GC: 按回收价值排序，优先回收高价值 Region
```

**筛选回收阶段的精髓**：

> 对各个 Region 的回收价值和成本进行排序，根据 `-XX:MaxGCPauseMillis` 指定的停顿时间制定回收计划。比如老年代 1000 个 Region 都满了，200ms 只能回收 800 个，那就只回收这 800 个——**把 GC 停顿严格控制在指定范围内**。

回收算法主要用**复制算法**，将 Region 中的存活对象复制到另一 Region，不会像 CMS 那样产生大量内存碎片。

> CMS 回收阶段与用户线程并发执行， G1 因内部实现太复杂暂未实现并发回收——不过到了 Shenandoah（可看作 G1 升级版）就实现了并发收集。

**Garbage-First 名字的由来**：G1 维护一个优先列表，每次根据允许的收集时间，优先选择回收价值最大的 Region。比如 Region A 花 200ms 回收 10M，Region B 花 50ms 回收 20M——G1 当然优先选 B。

### 1.4 G1 四大特点

![G1 收集器特点]({{ '/assets/img/jvm/g1-zgc/page2_img1.png' | relative_url }})

| 特点 | 说明 |
|------|------|
| **并行与并发** | 充分利用多核 CPU，缩短 STW 时间；部分阶段可与用户线程并发 |
| **分代收集** | 保留分代概念，可独立管理整个 GC 堆 |
| **空间整合** | 整体基于"标记-整理"，局部基于"复制"——无碎片 |
| **可预测的停顿** | 通过 `-XX:MaxGCPauseMillis` 指定期望停顿时间，默认 **200ms** |

> 停顿时间不是越低越好。设置 20ms 可能导致每次回收范围太小，收集速度跟不上分配速度，最终堆满触发 Full GC 反而更慢。**一两百毫秒是比较合理的值**。

### 1.5 G1 垃圾收集分类

| 类型 | 触发条件 | 回收范围 |
|------|---------|---------|
| **Young GC** | Eden 区放满，且预估回收时间接近 `MaxGCPauseMillis` | 年轻代 Region |
| **Mixed GC** | 老年代占比达到 `InitiatingHeapOccupancyPercent`（默认 45%） | 所有年轻代 + 部分老年代 + Humongous |
| **Full GC** | Mixed GC 过程中没有足够空 Region 承载拷贝对象 | 全堆（单线程，非常耗时） |

**Young GC 的智能触发**：并不是 Eden 满了就立即触发。 G1 会先计算回收需要多久——如果远小于 `MaxGCPauseMillis`，就继续扩大年轻代；直到预估回收时间接近设定值才真正触发。

### 1.6 G1 核心参数速查

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `-XX:+UseG1GC` | 启用 G1 | — |
| `-XX:ParallelGCThreads` | GC 线程数 | — |
| `-XX:G1HeapRegionSize` | Region 大小（1M~32M，2 的 N 次幂） | 堆/2048 |
| `-XX:MaxGCPauseMillis` | 目标暂停时间 | 200ms |
| `-XX:G1NewSizePercent` | 新生代初始占比 | 5% |
| `-XX:G1MaxNewSizePercent` | 新生代最大占比 | 60% |
| `-XX:TargetSurvivorRatio` | Survivor 填充容量阈值 | 50% |
| `-XX:MaxTenuringThreshold` | 最大晋升年龄 | 15 |
| `-XX:InitiatingHeapOccupancyPercent` | 触发 Mixed GC 的老年代占比 | 45% |
| `-XX:G1MixedGCLiveThresholdPercent` | Region 存活对象低于此值才回收 | 85% |
| `-XX:G1MixedGCCountTarget` | 筛选回收阶段次数 | 8 次 |
| `-XX:G1HeapWastePercent` | 空闲 Region 达到堆 5% 即停止混合回收 | 5% |

### 1.7 G1 优化建议

核心在于调节 `-XX:MaxGCPauseMills`：在保证年轻代 GC 别太频繁的同时，还得考虑每次 GC 过后的存活对象有多少，避免存活对象太多快速进入老年代，频繁触发 Mixed GC。

**如果停顿时间设太大**：系统运行很久才触发年轻代 GC，此时年轻代可能已占堆的 60%，存活对象会很多 → Survivor 放不下 → 大量进入老年代 → 频繁 Full GC。

**如果停顿时间设太小**：每次只回收少量 Region → 收集速度跟不上分配速度 → 垃圾堆积 → Full GC。

### 1.8 适用场景

| 条件 | 说明 |
|------|------|
| 50% 以上堆被存活对象占用 | 老年代占比高 |
| 对象分配和晋升速度变化大 | 流量波动剧烈 |
| 垃圾回收时间特别长（>1 秒） | 现有 GC 成为瓶颈 |
| **8GB 以上**堆内存 | 建议值 |
| 停顿时间要求 **500ms 以内** | G1 可以胜任 |

## 二、实战：高并发消息系统 JVM 优化

以 **Kafka** 为例，每秒处理几万到几十万消息，部署用大内存机器（如 64G），年轻代分配三四十个 G。

**问题**：三四十 G 的 Eden 区回收可能需要好几秒，而 Kafka 填满 Eden 只需一两分钟——意味着系统每运行一两分钟就会**卡顿几秒**，无法处理新消息。

**解决**：使用 G1 收集器，设置 `-XX:MaxGCPauseMills=50ms`。50ms 大概能回收三四个 G 内存，50ms 卡顿用户几乎无感知，系统就能在几乎无感知的情况下一边处理业务一边收集垃圾。

> G1 天生适合大内存机器的 JVM 运行，可以比较完美地解决大内存垃圾回收时间过长的问题。

## 三、 ZGC 收集器

`-XX:+UseZGC`（JDK 11 开始支持， JDK 15 后正式生产可用）

ZGC 是一款以**低延迟为首要目标**的垃圾收集器，源自 Azul System 公司的 C4 收集器。

### 3.1 ZGC 四大目标

![ZGC 目标]({{ '/assets/img/jvm/g1-zgc/page4_img1.png' | relative_url }})

| 目标 | 说明 |
|------|------|
| **TB 级堆** | 支持 TB 量级的堆，满足未来十年需求 |
| **停顿 < 10ms** | 最大 GC 停顿不超 10ms，且**不随堆增大而增长** |
| **奠定未来基础** | 为后续 GC 特性发展提供架构底座 |
| **吞吐降幅 < 15%** | 最坏情况吞吐量降低不超过 15% |

> **最大优点**：停顿时间不会随着堆的增大而增长！几十 G 堆停顿 10ms 以下，几百 G 甚至上 T 堆也是 10ms 以下。

### 3.2 暂时不分代

ZGC 目前是**单代**（不分代）。原来的垃圾回收器分代源于"大部分对象朝生夕死"的假设——分代实现起来麻烦，作者先实现一个简单可用的单代版本，后续会优化。

> **代价**：每次都需要全堆扫描，"朝生夕死"的对象不能及时被回收 → **浮动垃圾问题**。

### 3.3 ZGC 内存布局

![ZGC Region 类型]({{ '/assets/img/jvm/g1-zgc/page5_img1.png' | relative_url }})

ZGC 使用基于 Region 的内存布局，有三种 Region 类型：

| 类型 | 容量 | 用途 |
|------|------|------|
| **小型 Region** | 固定 2MB | 放置 < 256KB 的小对象 |
| **中型 Region** | 固定 32MB | 放置 256KB ~ 4MB 的对象 |
| **大型 Region** | 动态（2MB 整数倍） | 放置 ≥ 4MB 的大对象（每个仅存一个大对象，不会被重分配） |

### 3.4 NUMA-aware

NUMA（Non Uniform Memory Access Architecture）：每个 CPU 对应一块就近内存，优先访问本地内存，效率提升。

ZGC 能**自动感知 NUMA 架构**并充分利用其特性，在中大型系统上表现优秀。

## 四、颜色指针 — ZGC 核心设计

**Colored Pointers**（颜色指针）是 ZGC 的核心设计之一。以前的 GC 信息保存在**对象头**中，而 ZGC 的 GC 信息保存在**指针**中。

![颜色指针结构]({{ '/assets/img/jvm/g1-zgc/page6_img1.png' | relative_url }})

每个对象有一个 **64 位指针**，被分为：

| 位段 | 说明 |
|------|------|
| **18 位** | 预留给以后使用 |
| **1 位** | Finalizable 标识（只能通过 finalizer 访问） |
| **1 位** | Remapped 标识（对象未指向 relocation set） |
| **1 位** | Marked1 标识 |
| **1 位** | Marked0 标识 |
| **42 位** | 对象地址（支持 2^42 = **4T** 内存） |

![颜色指针再分配]({{ '/assets/img/jvm/g1-zgc/page6_img2.png' | relative_url }})

**为什么有两个 Mark 标记？**

每个 GC 周期开始时会交换使用的标记位，使上个 GC 周期中修正的标记状态失效：
- GC 周期 1：使用 Marked0，周期结束时所有引用标记为 01- GC 周期 2：使用 Marked1，期待标记 10，所有引用重新标记

![颜色指针标记周期]({{ '/assets/img/jvm/g1-zgc/page6_img3.png' | relative_url }})

**限制**：对象指针必须是 64 位 → ZGC 无法支持 32 位操作系统，也无法支持压缩指针（CompressedOops）。

> JDK 13 将最大支持堆从 4T 扩大到 **16T**（受限于主板地址总线 48bit，减去 4 位颜色 → 44 位 → 2^44 = 16T）。

**颜色指针三大优势**：

### 1. 某个 Region 的存活对象移走后，该 Region **立即可被释放重用**，不必等待所有引用被修正
### 2. 大幅减少内存屏障使用数量， ZGC **只使用读屏障**
### 3. 强大的扩展性，可存储更多与标记、重定位相关的数据

## 五、读屏障 — ZGC 关键特性

之前 GC 都采用 Write Barrier（写屏障），ZGC 采用完全不同的方案——**读屏障（Load Barriers）**。

在标记和移动对象阶段，每次**从堆里对象的引用类型中读取一个指针**时，都需要加上一个 Load Barrier：

```java
Object o = obj.fieldA;  // 从堆中读取对象引用 → 触发读屏障 Object p = o;           // 不从堆中读取 → 不触发 o.doSomething();         // 不从堆中读取 → 不触发 int x = obj.fieldB;     // fieldB 是原子类型 → 不触发
```

**自愈机制（Self-Healing）**：

```mermaid
graph TDA[读取堆中对象引用] --> B{颜色指针检查}B -->|Good Color| C[正常执行]B -->|Bad Color| D[Slow Path: 修正指针]D --> E[更新为新地址]E --> F[修正堆中字段]F --> C
```

如果对象在 GC 时被移动了，读屏障会把读出的指针**更新到对象的新地址**，并把堆里这个指针"修正"到原本的字段中。这样应用代码永远持有更新后的有效指针，而且**不需要 STW**。

> 类似 JDK 并发中的 CAS 自旋：读取的值发现失效了，需要重新读取。 ZGC 这里是之前持有的指针 GC 后失效了，通过读屏障修正指针。

![读屏障开头测试]({{ '/assets/img/jvm/g1-zgc/page7_img1.png' | relative_url }})

**代价**：Load Barriers 会导致吞吐量降低。官方测试数据需要多出额外 **4%** 的开销。

![读屏障开销]({{ '/assets/img/jvm/g1-zgc/page8_img1.png' | relative_url }})

## 六、 ZGC 运作过程

![ZGC 运作过程]({{ '/assets/img/jvm/g1-zgc/page8_img2.png' | relative_url }})

ZGC 的运作大致分为四个阶段：

```mermaid
graph TDA["① 并发标记<br>Concurrent Mark"] --> B["② 并发预备重分配<br>Concurrent Prepare for Relocate"]B --> C["③ 并发重分配<br>Concurrent Relocate<br>(核心阶段)"]C --> D["④ 并发重映射<br>Concurrent Remap<br>(合并到下次标记)"]
```

| 阶段 | 说明 |
|------|------|
| **并发标记** | 遍历对象图做可达性分析，**标记在指针上而非对象上**，更新 Marked0/Marked1 标志位 |
| **并发预备重分配** | 统计要清理哪些 Region，组成**重分配集（Relocation Set）**。ZGC 扫描所有 Region，用更大扫描成本换取省去 G1 的记忆集维护成本 |
| **并发重分配** | 核心阶段。存活对象复制到新 Region，为每个重分配集 Region 维护**转发表**。首次访问旧对象时读屏障截获，根据转发表转发到新对象，并修正指针指向新对象——**指针"自愈"** |
| **并发重映射** | 修正整个堆中指向旧对象的所有引用。由于"自愈"能力，此操作不紧迫——ZGC 巧妙地将它**合并到下一次 GC 的并发标记阶段**，节省一次遍历开销 |

> 由于指针"自愈"能力，只有**第一次访问旧对象会变慢**。重分配集中某个 Region 的存活对象都复制完毕后，该 Region **立即可释放**用于新对象分配，转发表保留直到所有访问都修正。

## 七、 ZGC 问题与参数

### 7.1 浮动垃圾问题

ZGC 停顿时间在 10ms 以下，但**执行时间**远大于这个时间。假如 ZGC 全过程需要执行 10 分钟，期间会创建大量新对象，这些对象只能在下次 GC 时回收——这就是**浮动垃圾**。

**根本原因**：ZGC 没有分代概念，每次全堆扫描，"朝生夕死"的对象不能及时回收。

**当前方案**：增大堆容量，让程序有更多喘息时间（治标不治本）。

**根本方案**：引入分代收集，让新生对象在专门区域创建，进行更频繁、更快的收集。（JDK 21 已实现分代 ZGC）

### 7.2 ZGC 参数设置

![ZGC 参数]({{ '/assets/img/jvm/g1-zgc/page9_img1.png' | relative_url }})

启用：`-XX:+UnlockExperimentalVMOptions -XX:+UseZGC`（JDK 15 后直接 `-XX:+UseZGC`）

ZGC 调优参数不多，大部分工作 JVM 能自动完成。

### 7.3 ZGC 四种触发机制

| 机制 | 说明 |
|------|------|
| **定时触发** | 默认不使用，通过 `ZCollectionInterval` 配置 |
| **预热触发** | 最多 3 次，在堆达 10%、20%、30% 时触发，统计 GC 时间 |
| **分配速率** | 基于正态分布，预测内存耗尽时间，在耗尽前触发 |
| **主动触发** | 距上次 GC 堆增长 10%，或超过 5 分钟，对比间隔时间 ≥ 49×最大 GC 持续时间则触发 |

## 八、如何选择垃圾收集器

```mermaid
graph LRA[内存大小] -->|< 100M| B[Serial]A -->|4G 以下| C[Parallel]A -->|4 ~ 8G| D[ParNew + CMS]A -->|8G 以上| E[G1]A -->|几百 G 以上| F[ZGC]
```

![垃圾收集器选型]({{ '/assets/img/jvm/g1-zgc/page10_img1.png' | relative_url }})

| 场景 | 推荐收集器 |
|------|-----------|
| 内存 < 100M | Serial 串行收集器 |
| 单核、无停顿要求 | Serial 或 JVM 自行选择 |
| 允许停顿 > 1 秒 | Parallel 并行收集器 |
| **响应时间最重要、停顿 < 1s** | **并发收集器** |
| 4G 以下 | Parallel |
| 4~8G | ParNew + CMS |
| 8G 以上 | G1 |
| 几百 G 以上 / 超低延迟 | ZGC |

> JDK 1.8 默认：**Parallel**（年轻代+老年代）
> JDK 1.9 起默认：**G1**

## 九、安全点与安全区域

### 安全点（Safe Point）

GC 不是想什么时候触发就立即触发的，需要等待所有线程运行到**安全点**后才能触发。

> JVM 设置一个标志位，各线程执行时不断主动轮询这个标志，一旦发现中断标志为真就在最近的安全点上主动挂起。

**安全点位置**：方法返回前、调用方法后、抛出异常位置、循环末尾。

### 安全区域（Safe Region）

如果一个线程处于 **Sleep / 中断状态**，它无法响应 JVM 的中断请求，无法运行到 Safe Point。因此引入 **Safe Region**：在一段代码片段中引用关系不会发生变化，此区域内任意地方开始 GC 都是安全的。
